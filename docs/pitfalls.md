# 既定値のままでは動かない — ローカルLLMを編集業務に入れるときの落とし穴

すべて実機で踏んだもの。共通するのは **エラーにならず静かに失敗する** こと。
HTTP は 200 を返し、空文字列や切り詰められた入力で処理が進む。
自力で環境を組むと、ここで数日失う可能性がある。

## 1. `num_ctx` の既定は 4096

ollama の既定文脈長は 4,096 トークン。実際の入力はこれを大きく超える。

| 入力 | 実測トークン数 |
|---|---|
| 投稿規定（BPPB Instructions for Authors） | 7,604 |
| 投稿規定 + 原稿1本 | 12,213 |
| 論文全文（arXiv:2512.17597） | 65,536 |
| 論文全文 + 指示 | 71,230 |

**超過分は黙って切り詰められる。** モデルは正常に応答を返すので、冒頭が失われている
ことに気づけない。規定チェックなら 65,536、査読補助なら 131,072 が必要。

### トークン数を文字数から見積もってはいけない

この検証で最初に犯した誤り。論文本文は **2.48 文字/トークン**（LaTeX 由来のテキストは
数式記号と短い断片が多い）。よく使われる「4文字/トークン」で見積もると **1.61 倍の
過小評価**になり、`num_ctx=65536` で足りると判断してしまう。実際には窓を埋め切って
文脈シフトが起き、**モデルが論文について書いている最中に論文の冒頭が追い出されていた**。
必ず実測する（`/api/chat` の応答に `prompt_eval_count` が入っている）。

## 2. `num_predict` は `num_ctx` との整合が必要

`num_predict` を増やすだけでは効かない。`num_ctx` − 入力トークン数 が出力の上限になる。
`num_ctx=32768` で入力 12,213 なら出力に使えるのは約 20,555 なので、
`num_predict=24576` は **到達不能**。しかもエラーにならず、文脈窓の上限で切り詰められる。

## 3. 「問題のない原稿」のほうがトークンを食う

| モデル | 違反40件の原稿 | 適合原稿 |
|---|---|---|
| qwen3.6:35b-a3b-bf16 | 11,084 | **15,442** |
| qwen3.5:35b-a3b-bf16 | 11,066 | **24,576（上限到達、出力ゼロ）** |

違反が見つからないと探し続けるため 1.4〜1.5 倍消費する。
**投稿原稿の多くはおおむね適合しているので、これが最頻ケースかつ最も失敗しやすい。**
違反だらけの原稿だけでベンチマークを取ると、この落とし穴は見えない。

## 4. 推論強度にはモデルごとの上限がある

| モデル | low | medium | high |
|---|---|---|---|
| gpt-oss:120b (65GB) | 11/40 (49s) | **14/40 (115s)** | **出力ゼロ (751s)** |
| gpt-oss:20b (13GB) | **9/40 (34s)** | 出力ゼロ (527s) | 出力ゼロ (529s) |

段階的に劣化せず崖から落ちる。ollama の既定は medium 相当なので、
**gpt-oss:20b は既定のままでは動かない**。
同じ medium で 120b は 3,273 トークンで結論に達し、20b は 24,576 使って何も返さない。
推論強度は絶対的な設定ではなく、モデル容量との相対で効く。

```
gpt-oss:20b  -> think: "low"
gpt-oss:120b -> think: "medium"
```

失敗が予算不足に見えるのが厄介で、上限を上げても解決しない。

## 5. 分割GGUF は3段階で詰まる

HuggingFace の GGUF を使う場合、Q4 以上の大きいモデルは分割されていることが多い。

1. `ollama pull hf.co/<repo>:<quant>` が**分割GGUFを拒否する**
   （`This tag is a sharded GGUF`、[ollama#5245](https://github.com/ollama/ollama/issues/5245)）
2. 手元にダウンロードして `ollama create` すると、**シャード1だけを黙って取り込む**。
   `ollama show` は 81.2B（実際は 106B）と表示し、推論すると HTTP 500。
   サイズ表示だけ見て「少し小さいな」で済ませると、壊れたモデルで測定を続けることになる。
3. llama.cpp の `llama-gguf-split --merge` で正しく結合しても、
   **チャットテンプレートの推論タグ処理が失われる**。`<think>...</think>` が本文に
   混入し、JSON パーサが失敗する。`ollama show` の Capabilities も `completion` のみになる。

単一ファイルの選択肢が Q2 以下しかないモデル（GLM-4.5-Air など）では、この経路を
避けられない。arm64 のリリースバイナリ（13.5MB、ビルド不要）で結合できる。

## 5b. `ollama pull` は失敗しても終了コード 0 を返す

最新のモデルを古い ollama で引くとこうなる。

```
Error: pull model manifest: 412:
The model you are attempting to pull requires a newer version of Ollama.
```

**それでも終了コードは 0。** バッチで回すとログに `rc=0` と記録され、成功したように見える。
実際にはモデルは存在せず、後段の実行フェーズで静かにスキップされる。
本検証では `qwen3.8:27b` と `gemma4` の2モデルがこれで欠落し、
実行フェーズの `[skip] ... not pulled yet` で初めて気づいた。

対策は終了コードを信じないこと。取得後に `ollama list` に実在するかを確認する。

```bash
ollama pull "$m"
if ! ollama list | awk 'NR>1{print $1}' | grep -qx "$m"; then
  echo "*** $m NOT PRESENT ***"
fi
```

## 5c. ツール呼び出しと推論タグは手動取り込みで失われる

`ollama show` の Capabilities を見ると、通常経路で入れたモデルは
`completion vision tools thinking` を報告するが、分割 GGUF を手動マージして
`ollama create` したモデルは **`completion` のみ**になる。
チャットテンプレートに含まれるツール定義も推論タグの扱いも失われるため、
そのモデルは外部照会を使うパイプラインに組み込めない。

## 6. Qwen3.5 世代は「問題ありません」に到達できない

| 入力 | 結果 |
|---|---|
| 違反40件の原稿 / 矛盾10件の原稿 | 正常終了 |
| **適合原稿 / 矛盾のない対照原稿 / 答えが明示された日本語10問** | **出力ゼロ**（918〜1,208秒） |

5例すべてで「見つけるものが無い」入力。プロンプト形式を変えても起きる。
同世代の Qwen3.6 は同じ入力で正常終了するので、**Qwen3.5 は使わない**。

## 7. プロンプトキャッシュが速度計測を汚染する

同一の接頭部（投稿規定など）を持つ2回目以降のリクエストは prefill が跳ね上がる
（1,325 → 2,940 tok/s、極端な例では 518,067 tok/s という無意味な値も観測）。
速度を測るならモデルをアンロードしてキャッシュを捨てる。

実運用ではこれは利点で、投稿規定は原稿が変わっても不変なので2本目以降が速くなる。

## 8. 出力が JSON でない場合に備える

- **スキーマ破綻**: GLM-4.7-Flash は配列の途中で JSON を放棄し自由記述に切り替わる。
- **キー名の相違**: 指定したキーと違う名前で返す。
- **隣接する文字列リテラル**: コンマなしで2つの文字列を並べる（引用を続けようとして）。
- **型の相違**: 文字列を期待する欄にリストを返す。

生の応答を必ず保存しておけば、GPU 時間を使い直さずに後から回収できる。
この検証では18セルを回収した。

## dense と MoE の decode 差は、プロンプト長で縮む

同一条件（prompt 約 4.3k、target 4k）での比較:

| モデル | 種別 | decode tok/s |
|---|---|---|
| `qwen3.6:35b-a3b-q8_0` | MoE、active 3B | 43.3 |
| `nemotron` | dense 42 GB | 4.6 |

約 9 倍差だが、これは 4k の条件での値である。プロンプトを伸ばすと差は縮む。

| prompt | MoE | dense | 比 |
|---|---|---|---|
| 4,317 / 4,256 | 43.3 | 4.6 | 9.4× |
| 14,729 / 14,107 | 41.1 | 4.3 | 9.6× |
| 65,536 | 4.3 | 3.2 | **1.3×** |

65k では MoE 側も 4.3 tok/s まで落ちる。長文入力では KV キャッシュの読み出しが支配的に
なり、active パラメータ数の優位が消える。**「MoE は dense より一桁速い」と一般化しては
いけない。** 速度比を引用するときは、必ずプロンプト長を添えること。

編集業務への含意: 規定適合チェック（T1、prompt 約 12k）は MoE が有利な領域にあるが、
査読支援（T2、prompt 約 79k）はそうではない。
